### 2026-10-15 · [新增] T04：选择性 ETC2/KTX2 纹理压缩和 JPG 回退

- **原因/需求：** 在不破坏 T02 法线生成和 T03 延迟加载的前提下，评估纹理压缩能否减少传输体积及 GPU 纹理占用。
- **具体变更：** 新增 `npm run textures:encode`、离线 ETC1 兼容 ETC2 RGB8 + mipmap + Zstd 的 KTX2 编码脚本及清单；根据体积（不大于 JPG 的 95%）与编码质量（PSNR ≥27 dB）选择天王星、海王星、木卫四共 3 张资源。`textureManager.js` 在 WebGL2/ETC2 支持时按需动态加载 `KTX2Loader`，失败时自动退回 JPG，再失败保留原有程序材质；地球、月球、火星继续走 JPG 以支持 T02 运行时生成法线。所有原 JPG 保留。
- **影响文件：** `scripts/encode-etc2-ktx2.mjs`、`src/data/compressedTextures.json`、`public/textures/ktx2/`、`src/universe/textureManager.js`、`src/universe/createSolarSystem.js`、`src/core/UniverseApp.js`、`package.json`、`README.md`、`public/textures/ATTRIBUTION.md`。完整方案与量化数据见 `docs/plans/2026-10-15.md#t04`，未完成与待验收清单见 `docs/DEVELOPMENT_PLAN.md`。
- **验证：** 13 张候选中仅 3 张满足阈值；其源 JPG 合计 584,103 B，预制 KTX2 合计 418,842 B（传输减少 28.3%）；所选三张 ETC2 mipmap 纹理约 3.14 MB，对比同规格 RGBA8 理论约 25.09 MB（估算减少 87.5%）。KTX2 结构回读、逐级 Zstd 解压与块长度校验通过；`npm run build` 通过（KTX2Loader 延迟分包约 59.14 kB）。本地浏览器已可进入太阳系并聚焦天王星。
- **备注：** 浏览器截图无法证明实际使用 GPU ETC2（而非 JPG 回退）；仍待 Network/DevTools、纹理接缝/朝向、不支持设备回退及手机 FPS/显存验收。未提交或推送 Git。**下一条 T05** 须由用户确认 T04 并再次发送“继续下一条”后开始。

## 固态天体表面法线与近景细节开发方案（T02）

> 日期：2026-10-15  
> 任务：T02 / P0  
> 状态：代码已完成、构建通过；桌面/手机近景视觉待用户验收  
> 范围：地球、月球、火星的表面材质与近景光照

### 1. 背景

当前太阳系已具备天体本地彩色纹理、受光材质、地球云层和大气、地球夜侧城市灯光，但 `MeshStandardMaterial` 没有 `normalMap` / `bumpMap`，近景地貌主要靠颜色变化表现。

### 2. 目标与界限

- 地球、月球和火星增加基于纹理的细微法线扰动，近距离光照呈现地貌层次。
- 保留原有高质量本地彩色 JPG 映射、地球云层、夜侧城市灯光和大气光晕。
- 使用现有颜色贴图的明暗和地球海陆色差，**估算**用于视觉演示的高度梯度，再生成切线空间 `normalMap`；不把估算纹理当作真实高程或科学测绘结果。
- 兼容程序化底图：彩色 JPG 加载失败时，继续使用原有 CanvasTexture 底图，并从该底图尝试建立法线；若法线生成失败则保持原材质正常显示。
- 只处理三个目标，控制额外纹理分辨率和显存；不提前实施 T03 的贴图按需加载、T04 的 KTX2 压缩或 T07 的自适应质量策略。

### 3. 实施步骤

| 优先级 | 内容 | 位置 |
| --- | --- | --- |
| P0 | 增加颜色图 → 估算高度 → 生成 RGB 切线空间法线图的工具，做海洋平坦化、横向 UV 接缝处理，控制法线强度及分辨率 | `src/universe/surfaceDetail.js` |
| P0 | 在地球、火星、月球彩色贴图应用后装配 `normalMap`，保留已有程序化贴图回退并对失败情况进行安全处理 | `src/universe/createSolarSystem.js` |

### 4. 验收标准

## 切换天体时镜头卡顿与抖动整改方案

> 日期：2026-10-15

1. `focusBody()` 的 GSAP `onUpdate` 独立读取目标天体位置并直接移动镜头；`animate()` 则在另一条 `requestAnimationFrame` 循环中推进天体公转。相机有机会按不同帧次的世界坐标取景。

## 运行中天体标签跟随流畅度优化方案

> 规划日期：2026-10-15  
> 状态：代码已实施、生产构建通过；浏览器动态效果与实机验收待完成  
> 范围：银河系标记、太阳系行星与卫星名称标签

### 1. 问题与依据

当前 Three.js 场景按 `requestAnimationFrame` 逐帧更新，但 `src/core/UniverseApp.js` 原先只在 `frame % 3 === 0` 时运行 `updateLabels()`。在 60 FPS 下，天体和相机约每秒变化 60 次，而 DOM 标签每秒仅跟随约 20 次，拖动、自动旋转和轨道运行中容易表现为跳动。

原先每次 `updateLabels()` 都读取多枚标签的 `offsetWidth`、`offsetHeight`。提高更新频率时，需要减少此类可能触发布局读取的操作。

### 2. 优化目标

- 标签位置与当前渲染帧的天体和相机保持同步，不再每隔三帧跳跃。
- 保留原有天体标签开关、卫星过滤、可视区域和相互避让规则。
- 避免给标签增加位置插值导致的跟踪拖尾，不因提升标签频率明显增加移动端布局开销。

### 3. 实施方案

| 优先级 | 内容 | 实施情况 |
| --- | --- | --- |
| P0 | 在 `animate()` 完成场景渲染后每帧运行 `updateLabels()`，使用同帧相机投影值定位标签 | 已实施 |
| P0 | 标签位置采用 CSS `translate3d` 更新，以便浏览器使用合成层处理位移 | 已实施 |
| P0 | 使用 `WeakMap` 缓存各标签宽高，以 `ResizeObserver` 在尺寸发生变化时失效缓存；窗口变化时同步清理 | 已实施 |
| P1 | 避免对每个天体重复计算当前目标是否为卫星 | 已实施 |

## 手机端与小屏幕响应式布局整改方案

> 规划日期：2026-10-15  
> 状态：**代码已实施，基础浏览器验证通过，完整交互与实机验收待完成**  
> 项目：COSMOS ATLAS / `D:\codex项目\threejs-universe`  
> 依据：本地 `index.html`、`src/styles.css`、`src/exploration.css`、`src/main.js`、`src/core/UniverseApp.js` 静态检查。尚未进行设备实测或浏览器可视化验收。

### 1. 背景及主要问题

目前界面采用覆盖在全屏 Three.js Canvas 之上的绝对 / 固定定位元素。桌面观感较完整，但当手机屏幕变窄或高度缩短时，首页文案、顶部场景导航、底部时间控制、行星列表和详情卡同时占用画面，影响星体观察和触控。

静态代码可见的关键风险如下：

| 区域 | 现有情况与代码依据 | 影响 |
| --- | --- | --- |
| 首页文案 | `src/styles.css` 的 `@media (max-width: 640px)` 将 `.hero-panel` 放在 `top: 22%`，标题字号 `clamp(45px, 11vw, 72px)`，描述、按钮与指标仍会显示 | 小屏首页文字容易覆盖银河的主要展示区 |
| 顶部导航 | 手机端 `.topbar` 高 `105px`，`.view-nav` 另放在 `top: 63px` | 顶部固定区域过高，压缩 3D 有效空间 |
| 底部栏 | `.bottom-interface` 在宽度 ≤640px 时改为竖向堆叠，仍同时包含时间控制和完整行星横向列表 | 固定底栏长期占用较多垂直空间 |
| 详情面板 | `.detail-panel` 手机端固定在底部栏上方，`bottom: 210px`，高度使用 `31vh` 等规则；`src/exploration.css` 用 `data-sheet` 控制三态 | 详情、底栏与顶部文字在短屏上挤占场景；三态高度与实际可用空间缺少统一管理 |
| 镜头构图 | `src/core/UniverseApp.js` 的 `focusBody()` 根据 `window.innerWidth <= 640` 和固定比例 `focusShift` 定位天体 | 抽屉状态、动态浏览器工具栏、横竖屏变化后可能出现天体被遮挡 |
| 天体标签 | `updateLabels()` 对顶部、底部、文字和详情框做了避让，但标签包围盒尺寸近似固定、保护区未统一纳入其它浮层 | 标签仍可能拥挤，尤其是狭窄视口 |
| 小屏弹窗与手势 | 弹窗分别使用 `80vh`/`86dvh` 高度限制；资料抽屉通过把手监听 `pointerdown` / `pointerup` | 需要检查虚拟键盘、刘海屏安全区、手势冲突及横竖屏下的可操作性 |

以上均为**代码层面的风险和整改依据**；具体遮挡的严重程度与实际设备表现还需要在实施阶段验证。

### 2. 设计目标与原则

**目标：让手机上 3D 宇宙/天体成为视觉主体，信息和控制随使用情境出现。**

- 保留现有深色宇宙主题、场景切换、时间控制、行星导航、搜索、自由漫游和天体资料功能。
- 默认状态尽量使 3D 的主要可视区域达到屏幕可用高度的 **60% 以上**；详情全屏展开时允许临时覆盖场景。该指标是拟定的验收目标，尚未实测。
- 主体天体不被持续性固定面板压住；点选、拖拽旋转、双指缩放应始终有足够的操作区域。
- 以**组件收纳和布局重排**为主，不单靠缩小字体；重要操作保持可辨识的字和足够的点击区域。
- 按有效可用高度、横竖屏、安全区、虚拟键盘和抽屉状态调整布局，尽量避免固定 `bottom: Npx` 相互依赖。

### 3. 建议的移动端界面结构

```text
┌────────────────────────────┐
│ COSMOS ATLAS       搜索  菜单 │  顶部：紧凑品牌与必要操作
│ 银河系     太阳系    自由探索  │  场景切换：单行、紧凑
├────────────────────────────┤
│                            │
│        3D 宇宙场景          │  中央：优先展示天体
│      可旋转 / 可缩放         │
│                            │
├────────────────────────────┤
│  ──                        │  天体详情：默认收起/摘要
│  地球 · Earth  关键数据   ↑  │  上滑：半屏/展开
├────────────────────────────┤
│ 播放  1×  轨道  星球  更多   │  底部：紧凑控制栏
└────────────────────────────┘
```

#### P0-A：首页文字减负

- 手机银河 / 太阳系首页保留简短标题、一个主要操作按钮；长段介绍与统计数据收入帮助/说明入口，减少重叠。
- 首页标题按**容器空间**和可用高度做分档，短屏减少文案块行数与上下间距。
- 自由漫游可显示极简按键提示，完整操作说明置于帮助面板；进入星球近景时主标题继续隐藏。

#### P0-B：底部控制栏收纳

- 手机端时间栏压缩为「播放/暂停、倍速、轨道/标签、更多」的单行或紧凑两行布局。
- 八行星导航改为可横向滑动的紧凑导航条，或通过“星球”入口展开；默认避免与时间控制形成两个高大面板。
- 保持搜索与天体切换的快捷入口，隐藏说明性文字而非降低关键文字到难辨程度。
- 所有可点控件建议以约 `44×44 CSS px` 为目标触控区域，触控区域可大于视觉图标。

#### P0-C：重构天体详情抽屉

- 继续沿用现有三态 `collapsed / half / expanded`：
  - **收起**：仅显示名称、一个关键参数与拖动把手；
  - **半屏**：显示简要介绍、基础参数与“查看更多”；
  - **展开**：完整资料、卫星列表、比较和导航，内容允许抽屉内部滚动。
- 根据**屏幕实际可用高度**统一计算抽屉上限，保留手势区域；去除详情面板与底部工具栏相互假设固定像素高度的问题。
- 切换卫星和重新聚焦时，保持抽屉状态逻辑一致并重置合适的滚动位置；避免手势与内部内容滚动互相抢占。

#### P0-D：相机与无遮挡区域联动

- 将顶部安全区域、底部工具栏和详情抽屉的实际矩形纳入**可见画面**计算。
- 银河 → 太阳系 → 地球近景的 GSAP 镜头动画，以及切换行星时，应将目标放在**无遮挡区域的视觉中心**，而非仅使用固定的竖向偏移。
- 抽屉收起/半屏/展开或横竖屏变化后，平滑更新镜头构图；避免视角突然跳动、天体穿模或打断自由拖拽。
- 桌面端保留当前镜头行为，通过统一的布局信息决定移动端偏移。

#### P1-E：顶部导航与横屏布局

- 窄屏顶部只展示品牌、搜索和菜单/设置，场景入口保留一行简短文字，必要时改为菜单。
- 手机横屏优先将控制项移至侧边或折叠浮层，最大限度留出画面高度。
- 使用 `env(safe-area-inset-*)`、`100dvh`/可用视口信息处理刘海屏、底部手势条与浏览器动态工具栏。

#### P1-F：标签、弹窗与可访问性

- 使用实际的标签文本宽高和遮挡区域做可视性判断；移动端限制同屏标签数，只优先显示当前目标或附近重要天体。
- 搜索、帮助、对比弹窗根据可用高度滚动，显示虚拟键盘时仍可关闭、切换目标。
- 检查焦点顺序、弹窗关闭后的焦点返回、系统大字体和 `prefers-reduced-motion` 情况。

## T04：KTX2 压缩纹理与兼容回退方案

> 日期：2026-10-15  
> 任务：T04 / P0  
> 状态：代码与压缩资源完成；浏览器 GPU 和真机待验收  
> 范围：GPU 压缩贴图、格式兼容、回退与传输/显存对比

### 1. 背景与现状

- 本地太阳系有太阳、八行星和七卫星共 16 张 JPG；T03 已实现按场景和聚焦对象请求，并保留程序生成底图。
- JPG 虽能节省传输，但 GPU 解码为普通 RGBA 后仍需较多显存；需要评估原生块压缩纹理。
- 当前 Windows 工作区未安装 `toktx` / `basisu`；终端外部下载受网络/代理限制，已有 FFmpeg、Node 22、Three.js。所用 Three.js `KTX2Loader` 能直接解析带 ETC2 `vkFormat` 的 KTX2 和 Zstd 超压缩，无需 Basis 转码器即可在支持 ETC2 的 GPU 上上传压缩块。
- 地球、月球、火星的 T02 演示性法线当前依赖从 JPG 的 HTMLImage 元素读取像素；压缩纹理无法直接作为 Canvas `drawImage` 输入。先保留这三颗的 JPG 路线，确保近景凹凸、粗糙度和回退不退化。

### 2. 实施方案

1. 利用 FFmpeg 读取本地 JPG 的 RGB 像素，Node 生成兼容 ETC2 的 RGB8 块压缩数据、逐级 mipmap，并存为标准 KTX2 容器；对每层进行 Zstd 传输压缩。
2. 记录压缩文件和源 JPG 的大小、压缩效果及估算 GPU 内存；只有压缩质量和文件体积满足预算时，才在运行时启用 KTX2，避免优化反而拖慢传输或产生严重纹理失真。
3. 加载前由 Three.js 检查 `WEBGL_compressed_texture_etc`；支持且存在预制 KTX2 时优先用 `KTX2Loader`，失败则退回本地 JPG，再失败保留程序材质。对不支持该扩展的设备直接走 JPG。
4. 与 T03 共用 Promise 缓存和两路并发调度，太阳、行星、卫星的加载优先级不变；`import.meta.env.BASE_URL` 保证本地及 GitHub Pages 子目录路径正确。
5. 纹理编码由离线命令完成，浏览器不会重新编码。保留全部现有 JPG 和署名，后续如取得 BasisU/UASTC 编码器可再评估通用转码方案。

### 3. 验收及限制

- 必须实际生成有效的 `.ktx2` 资源，并使用 Three.js 项目依赖的 KTX 解析器回读结构；不能仅添加加载器而标记完成。
- 生产构建须通过，报告实际 JPG/KTX2 大小差异，以及 ETC2 RGB8 约 0.5 字节/像素（不含 mipmap）与普通 RGBA 约 4 字节/像素的理论 GPU 内存差异。
- 三颗 T02 重点近景天体继续使用原 JPG，避免法线贴图失效；不支持 GPU 压缩、资源不存在或解码失败时走 JPG/程序底图。
- 网络瀑布图、实际压缩效果与跨桌面/手机设备 FPS/显存，需要浏览器实测。实施不包含 T05 星云动态。

### 4. 实施与验证记录

**2026-10-15 已实施：**

- 新增 `scripts/encode-etc2-ktx2.mjs`，`npm run textures:encode` 离线调用 FFmpeg 解码现有 JPG，以 ETC1 兼容的 ETC2 RGB8 块、完整 mipmap 和 Zstd 超压缩写出 KTX2；使用项目依赖的 KTX 解析器回读容器并校验尺寸、mipmap、压缩格式及解压后数据长度。无需在浏览器内编码或安装独立 Basis 工具。
- 新增 `src/data/compressedTextures.json` 记录候选体积、编码质量（PSNR）、GPU 估算显存和启用清单。编码候选共 13 张，只有质量 ≥27 dB 且 KTX2 文件不超过原 JPG 的 95% 才启用；**最终启用天王星、海王星、木卫四**。其余候选继续走 JPG，地球、月球、火星未纳入候选，保留 T02 表面法线生成。

## 性能采样、画质自适应恢复与降耗（T07）

> 日期：2026-10-15  
> 优先级：P0  
> 状态：**性能控制/诊断代码完成、生产构建通过；跨设备性能基准未执行**。

### 背景与目标

原代码持续低 FPS 时只降低 DPR，不会自动恢复；画质变化缺少粒子和后期处理联动。目标是控制移动设备负载，稳定时逐级回升，在后台暂停渲染，并提供可复现的 FPS 与渲染对象统计。桌面约 60 FPS、主流手机约 30 FPS 是**待测目标**。

### 实施方案与落地

1. `UniverseApp.js` 每约 1.3 秒采集 FPS 样本，保留最近 180 个；根据桌面/手机门槛累计低帧或恢复时长，分别通过 5 秒降级、18 秒恢复的迟滞机制和 10～12 秒冷却期避免频繁抖动。
2. 自动画质依次降低银河星点/尘埃、星云数量、背景星点、小行星实例数、太阳日冕粒子和可选 Bloom；最低档下继续逐步降低 DPR。帧率稳定后优先恢复 DPR，再恢复画质档位。手动低/高画质不触发自动调节。
3. `visibilitychange` 切后台取消渲染动画帧、清理活动移动键；返回前台跳过后台累积的时间差再继续渲染。
4. 新增只读 `window.getCosmosPerformance()`，返回即时/样本平均/样本最小 FPS、画质模式与档位、实际 DPR、draw calls、三角形/几何体/纹理数量。`gpuMemoryBytes` 明确为 `null`，因为 Three.js 渲染器统计**不能直接提供真实 GPU 显存字节数**；FPS 指示浮层提示当前渲染档位。

### 可重复的设备性能验收流程（待执行）

1. 分别使用一台桌面浏览器、主流 Android 与 iPhone Safari，记录设备型号、系统、浏览器版本、屏幕尺寸/DPR、电源模式和测试日期；关闭或记录其它高负载程序。
2. 每台设备依次测试「银河全景（30 秒）→ 太阳系（30 秒）→ 地球近景（30 秒）→ 木星/土星近景（30 秒）→ 自由漫游（30 秒）」，分别在自动、低、高画质记录结果；等待贴图加载和镜头动画结束，再开始稳定段统计。
3. 在浏览器控制台读取 `window.getCosmosPerformance()` 并记录 `fps`、`averageFps`、`minFps`、`samples`、`qualityMode`、`qualityTier`、`dpr`、`drawCalls`、`triangles`、`geometries` 和 `textures`。**样本平均与最小值为当前会话累积样本，场景间不会自动清零**；要获得单场景独立结果，应重新加载并等待稳定后采集，或使用浏览器性能面板录制。
4. 观察连续低 FPS 约 5 秒后的粒子分档/DPR 降级、持续恢复约 18 秒后的回升（加冷却等待）；手动切换画质验证不会自行改变档位；后台放置 30 秒再返回，确认无时间突跳或重复 RAF 循环。
5. 使用 DevTools Performance/Memory 与 WebGL/GPU 调试扩展分别采集首屏时间、纹理网络请求总量、CPU 内存与**支持时可观测**的纹理 GPU 占用；未能可靠测得 GPU 字节量时记为「不可用」，不可用 `renderer.info.memory.textures` 的数量替代显存。
6. 对比方案目标：桌面约 60 FPS、主流手机约 30 FPS，并观察画质切换是否影响银河动态、太阳系小行星和近景质量。任何设备/模式未满足目标时保存具体数据和瓶颈，不宣称普遍达标。
